# Phase 6E-B53H — `func_80076EE4` busy-DMA pump prefix

> Retail instruction words and byte strings in this file are elided (`xxxxxxxx`, `<N bytes …>`): no game data is committed. Read them from your own disc (`tools/extract/disc_cache.py`, EXE `SLUS_006.62`).

## Verdict and scope

**Architecture decision: A — BUSY-DMA PREFIX ONLY.**

B53H translates only the entry busy-DMA fast path of the retail libgpu
command-queue pump `func_80076EE4`. That is the exact canonical path: when
`func_80076C34` opportunistically pumps at `0x80076EA4`, the first LoadImage
DMA2 transfer is still in flight, so the pump reads CHCR, sees the busy bit,
and returns `1` without touching anything.

B53H does **not** translate the idle-DMA consumer path, complete or service
the in-flight transfer, dispatch a DMA IRQ, invoke a queued worker, advance
the consumer, deregister the callback, run DrawSync, or translate
`func_80077404` / `func_80074520` / `func_80077294`.

## ABI

```c

```

No instruction in the body reads `$a0`/`$a1` before writing it, and `$a2`

## The translated busy path

```text
80076EE4  xxxxxxxx  lui   v0,0x8009
80076EE8  xxxxxxxx  lw    v0,0x5860(v0)   ; D_80095860 = 0x1F8010A8 (DMA2 CHCR)
80076EEC  xxxxxxxx  addiu sp,sp,-0x20
80076EF0  xxxxxxxx  sw    ra,0x18(sp)
80076EF4  xxxxxxxx  sw    s1,0x14(sp)
80076EF8  xxxxxxxx  sw    s0,0x10(sp)
80076EFC  xxxxxxxx  lw    v0,0(v0)        ; CHCR — the FIRST state read
80076F00  xxxxxxxx  lui   s0,0x0100       ; 0x01000000 = bit 24 start/busy
80076F04  xxxxxxxx  and   v0,v0,s0
80076F08  xxxxxxxx  bnez  v0,0x80077130   ; busy -> shared epilogue
80076F0C  xxxxxxxx   addiu v0,zero,1      ; DELAY SLOT: the return value
...
80077130  xxxxxxxx  lw    ra,0x18(sp)
80077134  xxxxxxxx  lw    s1,0x14(sp)
80077138  xxxxxxxx  lw    s0,0x10(sp)
8007713C  xxxxxxxx  jr    ra
80077140  xxxxxxxx   addiu sp,sp,0x20     ; jr delay slot
```

The branch target is verified arithmetically: word `0x14400089` is
`bne $v0,$zero` with `imm = 0x0089 = 137`, so
`0x80076F08 + 4 + (137 << 2) = 0x80077130` — the shared epilogue. The
epilogue writes `$ra`, `$s1`, `$s0`, `$sp` and never touches `$v0`, so the
delay-slot `1` survives to the caller.

### Exact DMA-busy test

```text
*(volatile uint32_t *)0x1F8010A8 & 0x01000000
```

The mask is derived from `lui $s0,0x0100`, not from prose. The
discriminator is bit 24 specifically, not "CHCR non-zero": after an
explicit completion CHCR is `0x00000201` — still non-zero — and the pump
then takes the idle path. A dedicated test proves exactly that.

The function contains exactly six store instructions. Only three are on the


### Exact busy-path return

**`1`**, materialised in the branch delay slot at `0x80076F0C`.

Note this is *not* a unique sentinel: the non-busy return is
`(D_80095874 - D_80095878) & 0x3F`, which is also `1` when exactly one
entry is pending. A caller cannot distinguish the two paths by return
value — which is why the port uses an explicit completion signal rather
than a magic number (see "Boundary signalling" below).

## I_MASK verdict

The busy path performs **no I_MASK operation at all**, so there is no
exchange and therefore no restore obligation. The first
`jal func_80073E10` is at `0x80076F10`, eight bytes past the taken branch
at `0x80076F08`.

For the record, the untranslated idle path is sound in retail: exactly one
exchange (`0x80076F10`, argument 0), one save (`0x80076F30`, in the branch
delay slot so it is unconditional on that path), and one restore
(`0x8007709C`). There is exactly one `jr $ra` in the whole function, and
every idle-path branch converges on `.L80077094` before it, so no retail
path leaves an unrestored exchange.

The B53E bug class — a host run-control early return skipping a mandatory
restore — is absent here. The new early return added to
`func_80076C34_port.c` sits **after** the retail I_MASK restore, matching
retail order `0x80076E9C` (restore) → `0x80076EA4` (pump) →
`0x80076EAC..0x80076EC4` (pending count). A dedicated regression test
covers it.

## Boundary signalling

The port must know whether the pump actually returned, because the return
value cannot distinguish the busy path (`1`) from a one-entry pending count
(`1`). Inferring it from the host stop reason would be **wrong**:
`PE_Port_RequestStop` keeps only the *first* reason requested, so an
already-latched reason (for example a frame limit) would mask the pump's
boundary and let the dispatcher fabricate a pending count.

`PE_func_80076EE4_Pump(int *retail_returned)` therefore reports completion
explicitly; `func_80076EE4()` is the plain retail-ABI wrapper. A dedicated
test latches `PE_PORT_STOP_FRAME_LIMIT` first and proves the boundary is
still reported and no count is fabricated.

## Untranslated idle-DMA path (documented for the next rung)

Recovered in full but deliberately not implemented:

1. `0x80076F10` exchange I_MASK with 0; `0x80076F30` save the previous mask
   to `D_80095880` in the branch delay slot (unconditional on this path).
2. `0x80076F2C` if `producer == consumer`, jump to the restore block.
3. `0x80076F38..0x80076F4C` re-read CHCR; if it became busy, restore.
4. Loop head `0x80076F5C`: if `(consumer + 1) & 0x3F == producer` (this is
   the last pending entry) **and** `D_80095758` is zero, call
   `func_80073CF4(2, 0)` at `0x80076F90` — deregister DMA slot 2, because
   no interrupt is needed merely to drain an otherwise empty queue.
5. `0x80076FA4` read GPUSTAT; if bit 26 is clear, tight-poll at
   `0x80076FB8` with no timeout and no queue mutation.
6. `0x80076FCC..0x80077030` load `argument`, `auxiliary`, then the `worker`
   identity from `0x800BD034/38/30 + consumer * 96` — arguments are set up
   **before** the function-pointer load. `0x80077034` `jalr` invokes
   `worker(argument, auxiliary)`; the result is ignored.
7. `0x80077054` advance the consumer: `(consumer + 1) & 0x3F`.
8. `0x8007706C` if drained, restore; `0x8007708C` if DMA is still idle,
   loop back to step 4; otherwise restore.
9. `0x8007709C` restore I_MASK from `D_80095880`.
10. `0x800770B8`/`0x800770D8`/`0x800770F0`/`0x80077100`: only when the ring
    is empty, DMA is idle, the work marker is set, and a DrawSync callback
    is installed, `0x80077108` clears the marker **first** and `0x8007710C`
    invokes the callback with no arguments. (`$a0` incidentally still holds
    the callback address at the `jalr`; that is not an argument and must
    not be modelled as one.)
11. `0x80077114..0x8007712C` return `(producer - consumer) & 0x3F`.

Retail runs the entire drain — including the unbounded GPUSTAT spin and the
queued worker — with `I_MASK = 0`. `D_80095880` is a single non-reentrant
save slot; it is sound only because the mask is zero across that region,
which matters because the pump is itself the DMA2 IRQ callback as well as a
synchronous callee. Note also that `D_8009587C` (dispatcher) and
`D_80095880` (pump) are distinct slots, so the nesting does not clobber.

## How the pending LoadImage is supposed to complete — §20 answer

**Classification: DMA completion event integration + source-3 DMA IRQ
dispatch integration.** Both are required and they are one coupled
mechanism; neither exists in the port today.

The retail sequence is:

1. hardware DMA2 completion clears CHCR bit 24 and sets DICR channel-2
   completion flag bit 26;
2. that raises interrupt source 3, whose handler `func_80074520` was
   installed by `func_800744D4` via `func_80073CC4(3, func_80074520)`;
3. `func_80074520` reads `(DICR >> 24) & 0x7F`, acknowledges channel 2 with
   a W1C write that preserves the lower 24 bits, and `jalr`s
   `D_800956C0[2]` — which is `func_80076EE4`;
4. the pump now observes DMA idle, issues the queued second LoadImage
   through `func_80076664`, advances the consumer, and — once the ring is
   empty and DMA idle — clears the work marker and fires the DrawSync
   callback if one is installed.

In the port, step 1 already exists as B53B's explicit, deterministic
`PE_GPU_ServiceDMA2Completion(event_token)`, but **nothing calls it**:
there is no translated `func_80074520`, and the source-3 I_MASK
installation remains the deferred item recorded since B53F. So the missing
piece is a deterministic service opportunity plus a translated DMA IRQ
dispatch that invokes the guest identity in callback slot 2.

`func_80077294` (DrawSync) is a second, independent observation point that
would also drive completion, but it is not on the current execution path.

This answer determines B53I. B53H deliberately implements none of it.

## Oracle and tests

`tools/b53h_oracle.py` is independent of production C. It verifies the
executable SHA-1, file offset, range, body SHA-256, and all 152 literal
words; proves the busy branch target arithmetically; asserts that the
pre-branch prefix contains no call, no jump, no non-stack store, and no
load other than the CHCR pointer and CHCR itself; and checks the epilogue.
It verifies both MMIO pointer words, the exhaustive four-site caller
census, the two identity materializations, and that jump-table field
`+0x24` is never dispatched.

It then executes the words on a MIPS-I interpreter with exact delay slots,
with CHCR and GPUSTAT as **inert caller-supplied inputs**: reading them
never changes them, so an unready GPUSTAT reproduces retail's genuinely
unbounded poll rather than silently becoming ready. Scenarios: the
canonical busy case (return 1, zero guest writes, exit through the shared
epilogue, never executing past `0x80076F08`), repeated determinism, busy
with an empty queue, a CHCR sweep proving bit-24 discrimination in both
directions, idle+empty (exchange/restore with the exact mask), idle with
one entry (worker invoked once, consumer advances, slot 2 deregistered when
no DrawSync callback is installed and kept when one is), the completion
path (marker cleared before the callback fires exactly once), suppression
of the callback while DMA is busy, producer/consumer wrap 63→0, and the
unready-GPUSTAT poll.

Mutation probes confirm the oracle bites: corrupted literal word, wrong
busy mask, a model that auto-clears CHCR busy on read, a model that makes
GPUSTAT ready after the first poll, a tampered caller census, and a
tampered jump-table claim are all caught.

Eight production tests cover the ABI and canonical busy return, bit-24
discrimination (including an explicit completion, deliberately outside the
canonical path), full inertness under a whole-RAM canary plus VRAM samples
and a complete `0x60` entry comparison, eight repeated pumps with no
progress, dispatcher integration with the real pending-count return, the
frame-limit boundary-masking regression, strict advancement, and the stop
epoch. Eight pre-existing tests were retargeted from the removed boundary
to measured facts.

### The stop epoch — why the boundary signal is explicit

`PE_Port_RequestStop` deliberately keeps only the **first** reason, so the
reason value cannot tell a caller whether a specific callee just requested
a stop. B53H removes two places that inferred exactly that:

- the pump's own boundary is reported through an explicit
  `int *retail_returned` out-parameter on `PE_func_80076EE4_Pump`, so
  `func_80076C34_enqueue` never publishes a fabricated pending count when
  an earlier unrelated stop was already latched;
- the sibling direct-issue path at `func_80076C34_port.c` compares a new
  monotonic `PE_Port_StopEpoch()` across the worker call. Retail
  `0x80076D40..0x80076D4C` restores the saved I_MASK unconditionally when
  the worker returns, so an already-latched stop must not suppress that
  restore, and a genuinely new worker boundary must not be hidden by it.

`test_B53H_stop_epoch_distinguishes_latched_stops` proves both halves: the
epoch counts a second stop that the sticky reason does not, and a
pre-latched `PE_PORT_STOP_UNRESOLVED_BOUNDARY` — the same reason a real
worker boundary would use — still yields the worker's pixel write, an
unchanged epoch, and the exact I_MASK restore.
