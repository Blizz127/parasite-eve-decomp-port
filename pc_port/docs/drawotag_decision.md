# DrawOTag decision: guest builds the table, host walks it read-only

DrawOTag (`func_800753B4`: debug print, then `jtb[2](jtb[6], ot, 0, 0)`) and DrawOTagEnv (`func_800754E4`: build DR_ENV, splice `ot & 0xFFFFFF` into its tag, then the same `jtb[2]` dispatch) never interpret a primitive themselves — they hand the guest-RAM ordering table to the GPU-channel dispatcher that is already partially translated (`PE_func_80076C34_Inline8`, with the ring authoritative in guest RAM), exactly as the translated ClearOTagR (OTC1) already fills that same table with hardware-pattern terminator links plus AddPrim chains the field code writes. So the translation target is a read-only host walk of the guest table at dispatch time, consuming entries as data in the established display-buffer manner; if DrawOTag were instead host-adapted, the host would permanently own display-list ordering and every field primitive would stop being bytes the port reads and become control flow the port must reimplement — the difference between field rendering being a large but bounded table-walk plus a per-packet-type parser and being an unbounded reimplementation of the game's scene logic — and it would break the read-only presentation property the GPU rungs have held (no polling read evolves hardware; transients are consumed synchronously and never retained). Concretely: keep the existing `func_800754E4` shape (software tag splice + env cache), resolve its deferred `76C34(76B98)` cut by walking the `ot`-rooted chain from guest RAM, fence unsupported packet forms as mutation-free boundaries, and fix the known level-`>= 2` early-return defect in the partial port when that rung lands. (Done in DRW1 as print + stop + return, the `7506C` pattern; retail prints then continues — the stopped draw below the print is the documented residual, unobservable in production where the level is always 0.)
