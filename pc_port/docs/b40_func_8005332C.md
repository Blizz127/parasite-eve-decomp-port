## B39 call context

The B39 call is `func_80051CC4` site `0x80051D08`, its first nested
dependency and operation-map step 4.  The exact sequence is:

- `0x80051CC4`: save frame;
- `0x80051CCC`: `func_80052F0C()` saves whether the old table pointer differs
  from `0x800C0E48`;
- `0x80051CD4`: `func_80052E30(0)` installs the active table pointer/count;
- `0x80051CE0`: clear authoritative `D_8009D018`;
- `0x80051CE4..0x80051CFC`: clear seven words from `0x800A1B48` down to
  `0x800A1B30`;
- `0x80051D00/04`: `lui a0,0x800C; lb a0,0x0E22(a0)`, deriving one signed
  32-bit ID from guest byte `0x800C0E22`;
- `0x80051D08`: `jal func_8005332C`; `0x80051D0C` delay is `nop`;
- `0x80051D10`: copy return to `a2`;
- `0x80051D14`: NULL-check it; NULL skips to the later dependency;
- non-NULL is dereferenced at `return+0x14` for an unsigned command count,
  then at `return+0x15+i` for the command scan;
- `0x80051DD0`: the later `func_8005218C` boundary remains untouched.

Thus B39 commits its saved table kind, allocation state, command-mask clear,
and seven guest-word clears before the lookup.  It needs an exact guest
record or NULL afterward.  It never indexes or dereferences NULL and never
stores or transforms the returned address.  Every repeated B39 invocation
repeats the same clear/allocation/lookup sequence; it does not reuse a prior
record pointer.

## Dependency boundary

The only callee is translated B23 `func_8005DB44(unsigned int index)` at
`0x8005DB44`.  B40 calls it only for signed table entries `1..255`, with
the exact unsigned argument `entry-1` (`0..254`), and forwards its
`pe_addr_t` result unchanged.  B40 has performed only reads before the call
and has no partial write state.  The dependency reads guest words
`0x800A8038` then `0x800A8034`. Calling those values `base` and `alt`, it
computes `count=(base-alt)>>5`, returns zero when `index>=count`, and otherwise
returns the exact wrapped value `alt+(index<<5)+0x800A8028`. It performs no
write, makes no further call, and belongs to the same resource-record
subsystem. It is not unresolved, SDK-backed, or host-environment-backed. B40
therefore introduces no new boundary and does not translate a deeper
dependency. Its raw `lui 0x800B` plus signed
immediates `0x8038/0x8034` prove those `0x800A...` addresses. B40 corrects
the two prior native constants and the prior use of the loaded base where
retail retains the literal-address register; the retained B23 oracle already
modeled both facts correctly. B40 tests separately reject reads from the old
`0x800B...` aliases.

## Read/write footprint and authority

Direct persistent effects by path are:

- negative ID: no authoritative or guest data read;
- nonnegative ID: one 32-bit authoritative read of `D_8009D050`;
- in-range ID: then one 32-bit authoritative read of `D_8009D048`, followed
  by one signed 16-bit guest read at
  `D_8009D048 + ((uint32_t)resource_id << 1)`;
- delegated entry: dependency guest reads of four bytes at `0x800A8038`
  followed by four bytes at `0x800A8034`.

There are **no persistent writes**, so the exact direct-write footprint is
empty and every byte in the 2 MiB guest RAM is a write guard.  The MIPS
prologue's `sw ra`/`lw ra` at incoming retail stack minus eight are transient
ABI frame traffic, implemented by the native host ABI rather than guest
persistent state.

minimum `0x80000000` and maximum `0x801FFFFE`; the exact runtime address is
the wrapped expression above.  The dependency's fixed guest read range has

executable-data, hardware, GPU, DMA, MDEC, SPU, controller, disc, timer,
event, interrupt, BIOS, or Psy-Q access.  There is no loop, polling, wait, or
blocking behavior.  The result is not deterministic from guest RAM alone
